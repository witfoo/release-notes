# WitFoo Analytics 1.2.0

[L-001] **Released:** 2026-11-08 · **Previous:** 1.1.5 · **Type:** minor

## Summary

[L-002] WitFoo Analytics 1.2.0 completes the MCP connector and the controls around it. AI clients such as Claude Desktop, Cursor and Claude Code can connect to your appliance with a personal key that each user creates, or by signing in through the appliance's own OAuth 2.1 authorization server. Every connection acts as a real user with that user's permissions, and an administrator can see and end any of them. An optional relay, off until an operator turns it on with WFA 2.5.1 or later, gives an AI marketplace or MCP client an address that reaches the appliance's MCP endpoint through WitFoo, without opening an inbound port. The release also adds user-administration and session controls: users can be disabled and enabled again, sessions end when an account is disabled or its password changes, and the edge and the published ports are tighter. Signal Search applies the filters in its search bar to the whole time range and says when it read only part of it, and the Work Units page and many settings pages say what they hold and what they could not read. One new required setting, the key that seals stored secrets, needs your attention before you upgrade a Docker Compose stack. Upgrade recommended.

## Action required

### If you run Docker Compose or a standalone stack: set the key that seals stored secrets

- [L-003] **A new required setting.** The compose files no longer carry a default for `AUTH_CONFIG_ENCRYPTION_KEY`, the key that seals the secrets stored in the database (LDAP and SAML secrets, TLS keys, AI-provider keys, notification-channel configurations, audit-connector credentials and Vrax connection credentials). It is now required: every `docker compose` command refuses to run until it is set, and the services refuse to start with a value that is not 32 bytes of base64, or with the value earlier compose files used to ship. If you start your stack with the provided launch scripts, a key is generated for you and written to your `.env` when none is set. The key is part of your data: back it up whenever you back up the database, and store the two apart.
- [L-004] **If your stack was started from an earlier compose file and never set a key of its own**, the secrets it already stored are sealed under the value those files used to ship, and the new services need to be told so. Before you start 1.2.0, take a backup; set a new key in your root `.env` (a random 32-byte value, base64-encoded); and list the value the earlier files shipped as `AUTH_CONFIG_ENCRYPTION_KEY_PREVIOUS` in the same file. Then start everything with a single `docker compose up -d`, so the images, the new key and the previous key change together. If the previous key is missing, the stored secrets cannot be opened until you add it and recreate the api and incident-engine services. The procedure, step by step, is "A stack that never set the key" in the Configuration documentation; a stack that has stored nothing sealed has nothing to convert and only needs the new key.
- [L-005] **On more than one node, every node must carry the same two values.** Every node that runs the api or incident-engine against the same Cassandra cluster needs the same `AUTH_CONFIG_ENCRYPTION_KEY` and the same `AUTH_CONFIG_ENCRYPTION_KEY_PREVIOUS`. The launch script generates a key on any machine whose `.env` has none, so on a second node copy both variables from the first node's `.env` before its first start: a node that generated its own key cannot open what the first one sealed, and the first cannot open what it seals.
- [L-006] **The first start tells you what to do.** When the launch script has to generate the key, it says what that means for a stack that already holds data, and prints the one command that lists the value earlier compose files shipped as the previous key. It also reports, without changing it, a key that is set but would be refused by the services (not 32 bytes of base64, or the old shipped value).

### If you run a WFA-managed appliance: upgrade in this order

- [L-007b] **If WFA automatic updates are off on your appliance:** WFA 2.5.3 is published before the analytics 1.2.0 images. Update the analytics images to 1.2.0 first and install WFA 2.5.3 soon after (L-007); on an appliance coming from WFA 2.4.x, the first start of WFA 2.5.3 recreates every container (L-323), so plan it for a quiet period.

- [L-007] **Update the analytics images to 1.2.0, then WFA 2.5.3 soon after.** On an appliance WFA owns the encryption key, so do not edit it by hand. WFA 2.5.1 and later replace the key that seals stored secrets with a random one only once the appliance's analytics images are 1.2.0 (L-246l), so the order does not affect stored secrets. Install WFA 2.5.3 soon after the images: until a WFA of 2.5.1 or later runs, the Conductor DATA stream keeps the broker's two-minute duplicate window while the updated images already send a message id on every publish, so the broker holds about 30 KB of publish ids in memory for each artifact per second of ingest.

### If your Analytics administrator still has the default password (WFA-managed appliances)

- [L-007a] **WFA 2.5.1 and later may change the Analytics web UI administrator's password (admin@witfoo.com).** On the first start of WFA 2.5.1 or later, if that administrator still has the shipped default password: when the password file from `wfa configure`'s Admin Account step is still on the node, WFA applies it as the Analytics administrator password and signs the administrator's current sessions out; when the file is no longer there, WFA leaves the password as it is and logs a warning that names `wfa user-reset`. A password anyone has already set, in the web UI or with `wfa user-reset`, is never changed. This can take up to an hour while the database starts and does not delay the appliance start. Before you upgrade, make sure you know the password last entered at `wfa configure`, and update any script or integration that signs in as admin@witfoo.com with the default password. If you cannot sign in after the upgrade, run `wfa user-reset` on the node.

### If you run separate Conductor nodes: upgrade them with analytics or before it

- [L-008] Upgrade every Conductor, including separate or remote Conductor nodes, to 1.2.0 at the same time as analytics or before it. A Conductor on 1.1.5 or older sending to 1.2.0 analytics keeps only about one record per page or poll for Azure Security, Microsoft Sentinel, Cisco AMP, Cisco Umbrella, Cisco Meraki, Splunk and Stealthwatch, and the batch is still answered as accepted. All-in-one appliances upgrade both together. Conductors from before this release also send batches with no size bound, which a receiver on the small body profile (appliances with less than about 18.5 GiB of host memory) can refuse with 413.

### Ports, load balancers and the edge

- [L-009] Compose: NATS (4222, 8222, 6222), the api (8080), incident-engine (8083), the UI (3000), Prometheus (9090) and Grafana (3001) are now published on `INTERNAL_LISTEN_IP` (default 127.0.0.1) instead of `LISTEN_IP`. `LISTEN_IP` still publishes Cassandra (9042, 9160), the artifact receiver (8090) and the edge (443, 8888), so restrict Cassandra's ports at the host firewall.
- [L-010] With `WF_TRUSTED_PROXIES` unset, a TLS edge no longer believes any forwarder's `X-Forwarded-For`. An edge behind a load balancer (LB_MODE, or TLS disabled) keeps the old private-network list for one release, with a startup WARN. Customers behind a load balancer must declare it now: `WF_TRUSTED_PROXIES` on compose, or `trusted_proxies` in `node.json` on a WFA appliance (WFA 2.5.1 or later). A re-run of `wfa configure` or `wfa fetch` (including `wfa configure --license-file`) writes node.json without `trusted_proxies`: add it again after each re-run, then run `wfa restart`.
- [L-011] A load balancer that sends only `X-Real-IP` is keyed on its own address at the edge.
- [L-012] **Behind a load balancer, declare it before you enable the MCP exposure listener**: `trusted_proxies` in `node.json` on a WFA appliance (WFA 2.5.1 or later), or `WF_TRUSTED_PROXIES` on a standalone Docker Compose stack. Until it is declared, every client behind it shares one failed-authentication count on `/mcp`. A re-run of `wfa configure` or `wfa fetch` keeps the MCP settings but not `trusted_proxies`, so declare it again after each re-run.
- [L-013] On WFA appliances the api (8080) and incident-engine (8082) ports are no longer published on the host (WFA 2.5.1 or later).
- [L-014] On Conductor and AIO-Conductor appliances, WFA 2.5.1 and later publish port 2055/udp and open it in the host firewall for the NetFlow and IPFIX listener. The listener stays off until you enable it under Log Servers in the Conductor UI.
- [L-014a] Under WFA 2.4.x, port 2055/udp is not published on the host: publish it by hand as Configuration describes, or upgrade WFA to 2.5.3. The compose files in this release do not publish it either; on a Docker Compose stack add `2055:2055/udp` to the signal server's ports.

### If you use single sign-on, or you rely on a hand-typed Conductor address

- [L-015] Conductor UI: SAML sign-in now signs in only accounts whose Auth Source is SAML (SSO); an account whose Auth Source is Local or LDAP is refused. This applies to a Conductor node that serves its own sign-in page; on an all-in-one node, Analytics signs users in. Before upgrading a node whose Authentication Mode is SAML SSO, set each Local or LDAP account that signs in through SAML to the SAML (SSO) Auth Source (Conductor Admin, Users; the Users page lists it as Auth Mode). In SAML SSO mode the server refuses every local sign-in, so after the upgrade an account left on Local or LDAP cannot sign in at all, a local administrator included. The Users page does not let a Superuser change its own Auth Source, so if the only Superuser is one of those accounts, first create a second Superuser with the SAML (SSO) Auth Source, using the username that SAML sign-in derives for another person, and convert the first account from it; or switch Authentication Mode (Conductor Admin, Settings, General) to Local/SAML (Mixed), where an account whose local password you know can still sign in, until the accounts are converted. Instructions, including the way back for a node that was upgraded first, are in the Conductor documentation on docs.witfoo.com.
- [L-016] Console UI: SAML sign-in now signs in only accounts whose auth mode is SAML; a Local or LDAP account with the same username is refused. A SAML sign-in whose username (the e-mail address the identity provider sends) matches no account creates one, with the Staff role and no organization: review new accounts on the Users page and assign them an organization.
- [L-017] Platform administrators (accounts with the platform-administrator flag or a role with a platform permission, such as Platform Admin) no longer sign in through an organization's SAML SSO or LDAP directory by default. If your platform administrators use your own organization's SAML SSO, write that organization's ID to /witfoo/configs/operator-identity-org on the node that runs analytics-api-svc (owner root, mode 0644) and restart analytics-api-svc; only one organization can be named, and the file is read at start-up. See Configuration > Operator identity organization. LDAP sign-in of these accounts works only when the organization's ID equals the first part of the account's mail domain (holder@example.com signs in to the organization example); use SAML for them otherwise. An account refused through SAML sees "Your account cannot sign in right now".
- [L-018] While /witfoo/configs/operator-identity-org names your organization, only a platform administrator can change that organization's SAML or LDAP configuration.
- [L-019] The reverse proxy no longer serves the `/ingestion/` path. Conductors send artifacts to the analytics host directly by default (port 8443, or the internal port 8090 on an AIO plus Conductor appliance), so nothing changes for them. A Conductor whose artifact endpoint was typed by hand with an `/ingestion/` prefix now receives 404 and must be pointed at the direct address. An ingestion URL left in an older compose file or environment is ignored. Who may reach the ingestion listeners remains the operator's firewall and network placement.
- [L-020] An IPv6-only analytics Cassandra container now refuses to start (exit 2, 'container IP is empty or malformed') instead of starting with an empty seed list. An IPv6 address is accepted only through `CASSANDRA_BROADCAST_RPC_ADDRESS`.

### If you allow public self-registration

- [L-021] **Public self-registration needs a domain mapping, and creates inactive accounts.** The organization a registration request names is ignored. With `AUTH_PUBLIC_REGISTRATION_ENABLED` on, an account is created only when `AUTH_PUBLIC_REGISTRATION_DOMAINS` maps the address's domain to an organization (comma-separated `domain=organization` pairs, matched exactly, no wildcard); otherwise registration gives the same uniform answer and creates nothing, and a malformed entry rejects the whole map until it is fixed. An account created this way is inactive: an administrator must enable it (Users, Enable) before the person can sign in. The tenant is chosen by the e-mail domain and the address is not verified.

### If you use MCP clients, upgrade incident-engine and the dispatcher together

- [L-022] Upgrade incident-engine and the dispatcher together; if they are on different versions, most MCP tool calls fail with an 'unexpected status 401' error.

### If you used organization-wide MCP keys

- [L-023] **Org-wide MCP keys (`wfmcp_…`) are retired.** They no longer authenticate, and issuing one returns 410. Administrators can still list them and use **Revoke all legacy keys** to clean up.

### If you use custom roles for administrators

- [L-024] Analytics: the setup wizard's AI, DNS, frameworks and CyberGrid steps now require ai:manage, signals:manage, frameworks:write and cybergrid:manage respectively, together with settings:manage. The built-in Admin and Platform Admin roles are unaffected. An administrator on a custom role that holds settings:manage but not the matching permission now sees the step refused. A user with the Admin role can add the permission to that role in Role Management (Settings menu in the page header; the permissions appear there as Manage AI, Manage Signals, Write Frameworks and Manage CyberGrid), and the affected user must sign in again.
- [L-025] **Dashboards write permission.** Creating, updating, deleting and cloning a dashboard now need the dashboards:write permission (they needed only dashboards:read); marking a dashboard as a favorite still needs only dashboards:read. A custom role that was used to edit dashboards with dashboards:read alone must be given dashboards:write.

### If you run Conductor UI or Console UI with SECRET_KEY set

- [L-025a] **A session key that shipped with an earlier release or an example file is refused.** Conductor UI and Console UI refuse to start when `SECRET_KEY` holds the value earlier releases carried, the value the Console's example deployment files showed, or a value that is not a usable key. Before you upgrade, either unset `SECRET_KEY`, so the program keeps a key of its own in `.secret_key` beside its database, or set it to a new value of 64 hexadecimal characters (for example the output of `openssl rand -hex 32`). Keep `.secret_key` with the database: a program that finds its database without the file generates a new key, which ends every session.

## What's new

### Connect AI clients to your appliance (MCP)

- [L-027] **Connections by personal key, by app sign-in and over HTTP `/mcp` are off by default.** For HTTP `/mcp` it takes two switches, both closed until you open them: the organization's mode under AI Setup → MCP Authentication (the choices are **Browser chat sessions only**, the default; **Browser chat sessions and personal keys**; and **Browser chat sessions, personal keys and app sign-in**), and the HTTP transport on the appliance (`mcp_http_enabled`; without it `/mcp` is not served at all). Browser chat sessions work in every mode, for users who hold `mcp:connect`.

#### Personal keys

- [L-028] **MCP connections are per user.** Each user who holds the new **Connect MCP** (`mcp:connect`) permission creates personal keys under **Profile → Security → MCP connections**. A connected AI client can reach only the tools, and the actions, that user's own permissions allow. Admin and Platform Admin hold `mcp:connect` automatically, and so does any role that holds `mcp:manage`; grant it to anyone else through a custom role.
- [L-029] **Keys expire.** Each key lasts 1–365 days (default 90), chosen when it is created. Keys can be rotated, and are revoked when their owner is disabled. A user can hold at most 5 active keys.
- [L-030] **Keys go in a header.** Send `X-MCP-Key: wfmcpu_…` (or `Authorization: Bearer`). A personal key in a URL is refused.
- [L-031] **A personal-key POST to `/mcp` is one bounded request.** A personal-key POST to `/mcp` carries exactly one JSON-RPC request of at most 1 MiB, read within 15 seconds; a batch is refused with 400 and a larger body with 413.
- [L-032] **Key audit entries record the caller's address.** Personal MCP key audit entries (issued, rotated, revoked) record the caller's address, and the responses that return a new key's secret carry Cache-Control: no-store.
- [L-033] **Browser sessions on `/ws/chat` are permission-checked live**, need `mcp:connect`, close within a minute of the session expiring, and must carry `aud` and `exp` claims.
- [L-034] **Revocation takes effect on the next request.** Revoking a key, disabling a user or removing `mcp:connect` stops an active client on its next request; an idle WebSocket closes within a minute.
- [L-035] **WebSocket refusals are readable.** A refused WebSocket connection gets the real HTTP status and message (for example 401 "MCP key expired").
- [L-036] **Downgrading** below this release disables every personal key. Secret scanners that match `^wfmcp_` do not match `wfmcpu_`. The retired org-wide keys are not revoked on upgrade: revoke them (Revoke all legacy keys) before a downgrade if they must stay dead, because a 1.1.x build accepts them again.
- [L-037] Personal MCP keys that were revoked or have expired stay in the list for 90 days after they stopped working, and are removed when their owner next issues or rotates a key after that. One user's keys, active and inactive together, are held to 50 per organization: a user who holds 50 has the inactive keys that stopped working longest ago removed first, however recently that was, when they make a new key. A user can create at most 20 keys in an hour (a rotation counts as creating one).
- [L-038] **The key card says what is wrong.** On **Profile → Security → MCP connections** a key list that cannot be read shows an error and a Retry, never "no keys yet"; when the organization does not allow personal keys the card says so before you try, disables Create, does not offer Rotate, and shows an otherwise good key as not usable; and the three refusals the card names (the limit, a conflicting rotation, a key that is no longer active) are explained in all seven languages the product ships (the creation-rate refusal shows the server's English sentence). The key table an administrator sees under AI Setup says the same when its list cannot be read.

#### Sign in from apps (OAuth 2.1)

- [L-039] **Apps can sign in to the appliance with OAuth 2.1.** Set `mcp_public_url` and `mcp_oauth_ui_url` in node.json (and optionally `mcp_oauth_cimd`), turn on the HTTP transport (`mcp_http_enabled`), then choose **Browser chat sessions, personal keys and app sign-in** under AI Setup → MCP Authentication. An appliance that sets neither URL answers on `/mcp` without app sign-in and shows app sign-in as not available; once both are set to valid values and the transport is on, `/mcp` answers a request with no credential with a challenge for every organization, and only an organization that chooses the mode can use an access token. The node.json keys need WFA 2.5.1 or later; on Docker Compose or a standalone stack the same settings are `MCP_PUBLIC_URL`, `MCP_OAUTH_UI_URL`, `MCP_OAUTH_CIMD` and `WF_MCP_HTTP_ENABLED`.
- [L-040] **Users approve each app and can end it.** The consent page names the app, where the approval goes and what the app asks for; read access is the default and the ability to make changes is a separate, unchecked option. Users see and revoke their apps under Profile → Security → Connected apps, and are notified when a new app connection is created.
- [L-041] **Administrators control which apps connect.** They register clients (and mark one trusted) and set the policy for apps that publish a client metadata document, and they see and revoke every connected app in the organization. Moving the organization out of the mode revokes every connected app it holds at that moment (an approval in flight at that instant can escape the revocation, but nothing can use it until the organization chooses **Browser chat sessions, personal keys and app sign-in** again).
- [L-042] **Access is short-lived and bounded.** Access tokens last 15 minutes, refresh tokens rotate and end after 14 days unused or 90 days in all, a reused refresh token revokes the connection's refresh tokens, so the app has to sign in again (the exceptions, among them one retry within 20 seconds, are in the MCP authentication documentation), and each app's volume is limited per user.
- [L-043] **Operators filtering inbound traffic** must let the apps' requests reach `/mcp`, the discovery documents and `/oauth/token`; see "Putting it on the network" in the MCP authentication documentation.
- [L-044] **What app sign-in does not do.** There is no registration by the app itself, no custom-scheme return address such as `cursor://`, no client secret (every app is a public client), no flow other than the authorization-code flow with PKCE (`S256`; refresh tokens renew it), no binding of tokens to a client key (no DPoP or mTLS, so a refresh token is a bearer credential), and an access token is accepted at `/mcp` only.

#### Which licences include MCP

- [L-045] **MCP is included with Analytics Pro, Analytics Max and Reporter Pro.** On Analytics Lite or Reporter Lite a connection is refused with a clear message, a licence that has never been read, or names a product this build does not know, is never treated as refusing, and nothing is deleted: moving to an included licence restores access with the existing keys. AI Setup and Profile → Security show a notice that names your licence and the ones that include MCP, and the actions that would create something no client could use (creating or rotating a key, turning MCP on) are refused and disabled until the licence includes it, and approving an app sign-in is refused.

#### Reaching the appliance from a marketplace client

- [L-046] **An optional exposure listener for marketplace clients.** A separate, optional listener on port 8444 serves `/mcp`, the sign-in discovery documents and `/oauth/token` and nothing else, so it is the only listener a marketplace client needs to reach; for app sign-in the user's browser must also reach the consent page on the main listener. It is off until you set `mcp_exposure_enabled` together with `mcp_http_enabled`. The product does not restrict which sources can reach it: forward only that port, and restrict the sources at your perimeter or on the host. A client that checks the server certificate needs TLS terminated in front of the port by a proxy or load balancer that holds a certificate for the name you publish, and that proxy should be declared to the reverse proxy as a trusted proxy, or every client behind it shares one failed-authentication count on `/mcp`.

#### The tools

- [L-047] **44 MCP tools, each marked read-only or state-changing**, so a client can ask before it changes anything (28 read, 16 state-changing). Every call is checked against the connected user's live permissions: dashboards work for holders of the dashboard permissions, and the tools that record who acted record the connected user. Seven tools that earlier releases listed but that always failed are removed: `search_attachment_metadata`, `get_framework_controls`, `create_search_job`, `list_search_jobs`, `search_lead_rules`, `search_leads` and `manage_lead_rules`.
- [L-048] **Each tool's title is in both places a client reads it.** Every entry in `tools/list` carries the tool's title in `title` and in `annotations.title`, with the same text, so a client that reads either field shows the same name.
- [L-049] **The report tools report what they read.** A stored snapshot that is empty or unreadable is an error that names the report date, and every read tool carries the snapshot's confidence flag. `generate_report` holds the call open for up to five minutes, but the reverse proxy in front of HTTP `/mcp` closes a request at 120 seconds, so over HTTP `/mcp` a pass that takes longer ends in a transport error instead of the tool's answer; a pass that fails is an error result.
- [L-050] **MCP search answers say when they stop short.** `search_artifacts` says when an answer is not the whole result: `capped` is true when the answer filled its limit, so more may match; `next_offset` (present only then) is where the next page starts; `incomplete` and `incomplete_reason` (`partial`, `rows` or `time`) say when the search was cut short. `total` is still the number of artifacts in the answer. `search_nodes` says `capped` when a scan filled its limit. Each tool's description tells the AI client what these fields mean and what to do next, and the in-app assistant gets the same answers.
- [L-332] ChatGPT can now connect to an appliance's MCP endpoint; verified against a test rig, not yet against a live 1.2.0 appliance.

### Use the AI-connector relay

- [L-051] The AI-connector relay gives an AI marketplace or MCP client an address that reaches your appliance's MCP endpoint through WitFoo, without an inbound port on the appliance. It is off by default for every organization and every appliance; an operator turns it on for one appliance by running `wfa mcp-relay enable`, reading the notice below, typing ENABLE and running `wfa restart`.
- [L-052] **MCP relay (new, off by default).** An appliance can be reached by AI marketplaces and MCP clients through WitFoo's relay, with no inbound port. It needs WFA 2.5.1 or later (`wfa mcp-relay enable`), analytics 1.2.0 images, the MCP HTTP transport turned on, a licence that includes the MCP connector (Analytics Pro, Analytics Max or Reporter Pro), and outbound HTTPS to mcp-relay.witfoo.com on port 443.
- [L-053] **Network and sign-in requirements.** The relay connection uses no HTTP proxy, configured or ambient, and an appliance in offline mode cannot register. Only the MCP endpoint and its sign-in metadata and token paths are relayed; the consent page is not, so for app sign-in the approving user's browser must reach the analytics UI.
- [L-054] **The relay notice.** Turning the relay on shows this notice (version 2); you acknowledge it by typing ENABLE.
  - [L-055] **R1.** While the relay is on, your AI assistant's requests and your appliance's answers pass through WitFoo's relay service. The relay reads each one into memory to pass it on, so the sign-in tokens, personal keys and content in it can be read by the relay's software while they pass through. This applies to requests sent to the relay's address; an AI assistant that connects to your appliance's own address does not pass through the relay. Your appliance's own calls to the relay (to register, connect, acknowledge, report its status and revoke) also reach the relay readable, and carry your licence key or the relay credential.
  - [L-056] **R2.** The relay's address is served through Cloudflare, which acts as a proxy in front of WitFoo's relay. Cloudflare ends the encrypted connection at its network edge and passes the traffic on to WitFoo, so Cloudflare can also see what passes through: requests, answers, access and refresh tokens, personal keys, your licence key when the appliance registers, reports its status or revokes, and the relay credential when it connects and acknowledges. The registration and tunnel connections use the same address, so they pass through Cloudflare too. Cloudflare also sees the details of each connection: the network addresses of the caller and of your appliance, the time, the sizes, and the address's handle. Cloudflare keeps its own records of some requests, such as those its security rules block or limit, including the caller's network address and the path, for up to 30 days.
  - [L-057] **R3.** WitFoo's relay holds the content of requests and answers, and any token or key in them or sent with them, in memory only while it passes them on, and writes none of it to its database or logs. It keeps a one-way hash of the credential your appliance uses to connect for as long as the address exists. Its encrypted backups keep that hash until they are deleted: up to 37 days after the address is revoked, plus the time until the database's next clean-up (R4).
  - [L-058] **R4.** The relay's logs record, for each request, a request identifier, the address's handle, the method, the path, the time, the status, the sizes, the duration and the outcome. The method is the text the caller sent, kept up to 256 bytes, so a caller that puts anything other than a method there puts it in the log. They also record when a tunnel comes up or goes down, with the code that says why it closed, when an address is created, acknowledged or revoked, and an alert when a registering licence looks like a trial, cloud or offer licence. Some of those lines carry a short one-way fingerprint of your licence key or of the relay credential: the first eight characters of its SHA-256 hash. Until the address is revoked, the relay keeps a record of your organisation and appliance identifiers and the name your appliance gave as the person who switched the relay on. Anyone who holds your licence key can read that name. If your licence lapses, or your appliance is lost, the record stays until the address is revoked. The relay also keeps a second record of your organisation's entitlement (organisation, product, tier, expiry and the time it was last checked). It is rewritten about every 15 minutes while a tunnel is up. It expires 48 hours after it was last written and is removed from the database's storage 3 days after that write, plus the time until the database's next clean-up, so it can outlast a revocation. Event records that name the person who switched the relay on expire after 7 days and are removed from storage 8 days after they were written, plus the time until the database's next clean-up; the name kept in the first record above is not part of them, and stays until the address is revoked. Logs are kept for 30 days and are gone about a day after that. WitFoo backs up the relay's database every night, and again within an hour after an address is created or revoked. Each backup is encrypted before it leaves the relay's server, is stored in WitFoo's Oracle Cloud storage in Chicago, and is deleted automatically 35 days after it was made, or about a day later at most; the relay's server also keeps its own copy of each backup for up to 5 days. A backup holds the database's storage as it was when the backup was made, including records that had already expired or been cleared but were not yet removed from storage, so a record described in R3 and R4 can remain in a backup until that backup is deleted: up to 36 days after the record was removed from the database's storage. So that restoring a backup does not bring a revoked address back into use, the relay also keeps a list of when each address was created and revoked, naming only the address's handle, encrypted in the same storage and kept for the same 35 days.
  - [L-059] **R5.** The network address the relay sees for the machine that connects to it is passed to your appliance with each relayed request, so your own logs may record it, and a support pack made from those logs can reach WitFoo. The relay does not write it to its logs, database or metrics. It keeps it in memory as a rate-limit key.
  - [L-060] **R6.** The relay runs on Oracle Cloud Infrastructure in Chicago. Cloudflare handles the traffic at its own network edge, which may be outside that region.
  - [L-061] **R7.** It is off by default for every organisation and every appliance, and turning it on is your act on this appliance. A revocation made shortly before the relay's server is lost, and not yet copied off that server (which normally happens within about two minutes), can also be undone by a restore. ### Receiving artifacts

- [L-107] **Admission.** A request body is admitted holding nothing and is charged to a shared budget as it arrives; a body over the limit or over what the budget could ever hold is refused (413), a budget that is full answers 503 with Retry-After: 1 and Connection: close; nesting deeper than 64 (32 at the incident engine, 4 in a criteria list) is refused 400.
- [L-108] **Request line and headers.** Limited to 12,288 bytes in all (8 KiB plus the 4 KiB net/http adds) on every port it opens, was 20,480; over it, 431. The TLS port speaks HTTP/1.1 only (a client that offers only HTTP/2 fails its handshake).
- [L-109] **Message limit.** The largest artifact the receiver takes is now 9.5 MiB (9,961,472 bytes), the message bus's own 10 MiB less 512 KiB for what the receiver adds around an artifact (was 16 MiB on the WebSocket stream). An artifact above it is refused by the stream, and an exporter reports it and does not send it; an exporter sends a batch at 16 MiB (was 32 MiB). A Lumberjack (Beats) event above 9,945,088 bytes ends the connection (it was read, and refused later, when the limit was 10 MiB). WF_INGEST_MAX_MESSAGE_MIB above 9.5 is ignored with a note in the log.
- [L-110] **Batch routes.** A body whose list holds more than 1,000 artifacts is answered 400 with the same words as before ("batch size exceeds maximum of 1000 artifacts"), now before the body is priced or decoded; what else a body counts is still charged against the in-flight budget, and a body the budget could never hold is refused 413. The memory figures of the budget are restated from fresh measurements (peak resident size up to 2.25 times the budget): give the container a limit with room for more than that on top of a receiver at rest.
- [L-111] **Typed batch route and stream.** The host, message type and pipeline entrypoint an artifact carries are the sender's own; the receiver writes its own values (artifact-ingestion:8090, generic, http:8090) only for a field the sender left empty.
- [L-112] **Fairness between bodies and between senders.** One request body may be charged at most a quarter of the budget beyond four bytes of memory for each byte of its own length (64 MiB of the default 256 MiB, 32 MiB of the small profile's 128 MiB). A body that decodes to far more than its bytes (a very long array of tiny values) is refused 413 where it is priced, before it is decoded; ordinary text is not affected. One sender, read from the remote address of its connection (an IPv6 address as its /64, never from a header), may hold at most half of the budget at once (128 MiB on the default profile, 64 MiB on the small): a request that would take its sender past that is answered 503 with Retry-After and holds nothing, and a stream message past it closes the stream with 1013. Loopback and the addresses in WF_CONN_TRUSTED are exempt. An exporter's flush is 16 MiB of ordinary text and is charged 64 MiB, so one sender is served one flush at a time on the small profile and two on the default; the next at the same moment is answered 503, which the exporter reads as "send again later": a delay and not a loss.
- [L-113] **One event is stored once.** Redelivered copies of one Conductor event keep the Conductor's own id and are stored once.
- [L-113a] **Artifact ids are version-1 UUIDs.** At the typed batch route, the WebSocket stream and the Conductor batch route, an artifact id that is not a version-1 UUID is replaced with a new version-1 id, and the sender's id is kept as `source_time_id` (and used to drop duplicates); an artifact with no id gets one. The graph processor ends a message with any other id at once, without retries; such an artifact used to be retried and never stored. (See Known limitations: "Resent artifacts whose id was replaced".)

### Exporters and connectors (Conductor pipeline)

- [L-116] **Artifact exporter (analytics, reporter connectors): refused batches.** A batch the receiver refuses for what it holds (400, 413, 422) is divided until the artifact it refuses is found; an artifact refused sent alone is set aside (reported once, acknowledged, not sent again) only on evidence that the receiver works for others, else kept and given back to the stream after 30 s; three refused flushes in a row stop the instance with "the receiver refuses every artifact it is sent" and nothing is discarded. - [L-118] **Artifact exporter (analytics connector) batching.** A partial batch is sent 2 seconds after its first artifact, where the previous sender waited for its fetch; the receiver sees small batches more often (on a test appliance, about one batch every 5 seconds of 1 to 39 artifacts, instead of 2 to 3 a minute). - [L-146] **Disruption check, DISRUPTION_SKIP_SETTLED.** With DISRUPTION_SKIP_SETTLED on (the default), a check leaves alone an incident whose leads cannot have changed since the last check: one judged "not disrupted" for a reason that time cannot undo (no artifact ids, no leads, or no block action), whose artifact ids have not changed and for which no lead has been made since, found by one read of the leads made since the last check for each organization. A lead made while a check is running is acted on in the next check (about a minute later) for the incidents the skip passes over, where the full check may already see it in the same check. The processing nodes that make leads and the node that runs the check must agree on the time within 270 seconds (a margin of five minutes less the 30 seconds a write takes), because a lead is stamped with the clock of the node that made it; a lead stamped by a clock further behind than that is acted on at most four hours, plus the length of the check that reads it, after the incident's last full read, because every noted incident is read in full once in four hours. Memory is bounded: at most 200,000 notes (12 MiB) and, for one organization, the ids of at most 500,000 leads made since the last check (4.4 MiB); above that rate the check reads in full, as before. A restart starts with no notes: the first check reads every incident in full. DISRUPTION_SKIP_SETTLED=false is the full check of every incident, every time. ### Receiver capacity

- [L-232] **Receiver body profiles.** The receiver now has two body profiles. The default is a body of 64 MiB and an in-flight budget of 256 MiB; the small profile is a body of 32 MiB, a budget of 128 MiB and 1,024 stream connections. It is chosen by WF_INGEST_PROFILE=small or default, and when that is not set by the memory budget the appliance gives the container (WF_MEMORY_BUDGET_MB below 768 MiB runs the small profile: an appliance with less than about 18.5 GiB of host memory runs it). The receiver logs one line at start that names the profile and why.
- [L-233] **Receiver connection limits (new).** Each listener of artifact-ingestion holds at most a number of connections set from its memory budget (1,024 plain and 512 TLS once that budget reaches about 1.7 GiB; on a 32 GB appliance about 807 and 403, on a 16 GB appliance about 359 and 179), 64 metrics and 8 debug, and one source at most a share of them (128 plain and TLS, 16 metrics, 4 debug); a connection above either is closed at once, before a byte is read. Loopback is never held to the share. Settings: WF_CONN_MAX, WF_CONN_MAX_TLS, WF_CONN_MAX_PER_SOURCE (16 to 65536), WF_CONN_TRUSTED (CIDR list exempt from the share). **Operators: where more than about 40 to 60 conductors reach the receiver from ONE address (a NAT, a load balancer) or from one IPv6 /64, those conductors share 128 connections. A deployment that sets the receiver's environment itself can put that address or network in WF_CONN_TRUSTED. A WFA appliance has no setting for the WF_CONN_ variables in 1.2.0, so give those conductors more than one address, or more than one receiver, rather than put that many behind one address** (refused connections are retried by the exporter; nothing is lost, but throughput drops). Where the receiver's environment can be set, a fleet of more than 1,024 simultaneously connected conductors on one receiver raises WF_CONN_MAX / WF_CONN_MAX_TLS.

## Known limitations

- [L-294] **Leads storage.** The leads table keeps each organisation's leads in one storage partition, so a very large lead history in one organisation can slow lead reads.

- [L-300] **The demo-data container stops with a crash message.** Stopping the demo-data container logs a segmentation fault; it has no effect on your data.
- [L-301] **The Admin header overflows between 1056 and 1239 pixels wide.** At those desktop widths the header's actions can run past the right edge for an Admin.
- [L-302] **The Conductor dashboard's Container Status tab shows each container's run state only;** a container whose health check is failing still reads Running there (node status and problem reports do flag it).

On a busy appliance, the timeline can show only part of the window or no bars at all, and it says the result is incomplete.

If that is spent before the page is full, the search stops and says so, so a rare match in a long time range can be missing.
- [L-253] A search by offset returns at most its first 10,000 results: a request whose offset plus limit is more than 10,000 is refused, and the page shows "The search was not accepted as typed". Narrow the time range or add a filter to reach older events.
- [L-254] Typing ip=, port= or hostname= searches both sides at once: an event matches only when its client side and its server side both have that value. To match one side, use client_ip=, server_ip=, client_port=, server_port=, client_hostname= or server_hostname=.
- [L-255] On the artifact search API (not the Signal Search page), on the timeline and the facet counts, the client_ip and server_ip parameters apply an IPv6 address but not an IPv4 address (the result list applies both). To apply an IPv4 address on all three, send the same condition in the filters parameter, for example `filters=[{"field":"client_ip","operator":"=","value":"10.9.9.9"}]`.
- [L-257] **Work Units filters on a node, an ATT&CK technique or a Client IP read only that item's newest work units.** A node, ATT&CK technique or Client IP filter on Work Units (node_id, attack_technique_id, client_ip on GET /api/v1/incidents) lists only that item's newest work units, up to the limit (the page size in the UI), and total counts only those; beside a status, severity or Work Definition filter, meta.capped is true when that read comes back full.
- [L-258] **On-demand report generation does not cover an organization created after the appliance started.** The report scheduler reads the list of organizations once when the appliance starts; on-demand report generation for an organization created afterwards answers 409 until the appliance's services restart.
- [L-259] **The MCP Server Settings card saves controls that do not decide who is admitted.** AI Setup → MCP Server Settings saves MCP Server Enabled, Allowed Origins and Max Concurrent Connections without changing which clients are admitted; Rate Limit (requests/min) applies to apps that use app sign-in only. "Who can connect over MCP" under AI Setup → MCP Authentication decides who is admitted ("Browser chat sessions only" refuses personal keys and app sign-in), and WF_ALLOWED_ORIGINS sets browser origins.
- [L-260] Dashboard widgets whose data source is Work Units show no data: a counter reads 0, and a chart or a table is empty, although the Work Units page holds and shows the data. Widgets whose data source is Nodes or Edges show their data. A widget on the Artifacts source set to a fixed time range wider than your organization's search window (30 days unless Retention → Search is set), or to a range that ends before it starts, shows an error instead; narrow its range to clear it. A relative range (for example the last 90 days) is shortened to the search window instead.
- [L-260b] **Artifact dashboard widgets show "Not available yet".** In 1.2.0, dashboard widgets that count artifacts (signals), including the SOC Overview "Artifacts Today" and "Artifacts by Source" tiles, show "Not available yet" instead of a count, because the widget engine cannot read artifacts yet. - [L-260a] On the Operational Health dashboard, the Error Rate Trend and Error Count (24h) widgets read fields the health source does not carry: the trend shows its empty state and the count reads 0.
- [L-262] **Conductors behind one address share the per-source budget.** An exporter whose batch_size is raised to 1000 with artifacts of 16 KiB or more can be slowed behind one address (the second flush waits about 6 s more, the third about 21 s; two to four senders back to back lose about 38 to 42 percent of their throughput, one of them starved); the default batch size is not affected; a site that tunes batch_size up can list the address of its senders in WF_CONN_TRUSTED where it sets that variable; on a WFA appliance, which has no setting for it in 1.2.0, keep batch_size at its default; a flush of 8 MiB or less is not serialized.
- [L-263] **Conductor exporter on slow uplinks.** Every request has 15 seconds to complete, including the upload, so a flush near the exporter's 16 MiB bound needs an uplink of about 9 Mbit/s for that Conductor alone; below that every attempt times out, the flush is left unresolved (unacknowledged) and its messages come back after the 2-minute acknowledgement wait, with nothing delivered meanwhile and nothing lost. At the default batch size of 100 artifacts (a flush of a fraction of a MiB) this does not arise.
- [L-264] **Disruption check after a restart.** The first disruption check after a restart reads every active incident of the past year in full (about 11 minutes at 100,000 incidents of about five artifact ids each, measured on a test system); later checks leave settled incidents alone.
- [L-265] **Work units at the end of their year.** A work unit that is still being updated after its 365th day (an evidence removal or a recalculation on an old unit) keeps its title and status and loses its name, creation time and part numbers.
- [L-266] **Chat sessions after 90 days.** A chat session still in use after its 90th day can show as a blank entry in the session list, with its title and creation time gone. A fix is planned.
- [L-267] **Replay and the Escape key.** Holding the Escape key down on the replay closes an open detail window and then leaves the replay; press Escape once for each window.
- [L-268] **Settings that cannot be decoded.** When a connector run by the instance manager cannot decode the settings an operator supplied (for example the settings of the SCP transfer, the local file system, the reporter or Abnormal Security connectors), its health code is decode_error, a transient code, and the Conductor UI explains it with the same text as for a provider response that could not be decoded, although no provider was contacted and the instance does not retry the settings; the connector's own message, which names the settings, is shown in the detail.
- [L-269] **Conductor clock far ahead.** When a Conductor's clock runs more than 30 days ahead, a Signal Search that gives both a start and an end time (and no message type, stream or action filter) can leave that Conductor's events out of the results list, while the timeline, the facet counts and the statistics still count them.
- [L-270] **Work units and their edges.** A work unit can outlive its edge records: its Edges section can read "Edges (0)" above a table of edges, and an edge's detail can open empty.
- [L-271] **Dispatcher consumer repair.** A dispatcher event consumer left waiting ahead of its stream (for example after the stream was recreated) is repaired only when the dispatcher starts: restart the dispatcher to repair it. Events published while it was stuck are not replayed.
- [L-272] **Console configuration push.** A configuration pushed from the Console while only the node's Conductor UI is connected (and not its appliance helper) is marked sent, although nothing applied it.
- [L-273] **Console connection limit.** A node holds up to four Console connections; a fifth closes the oldest, whichever client (Conductor UI or appliance helper) it belongs to.
- [L-340] **File permissions on console and conductor nodes.** On console and conductor nodes, the console database and the TLS server and client keys are readable by local accounts on the appliance, and the UI session key is briefly readable when WFA starts. Limit shell access on appliances to administrators.
- [L-341] **A data node is missing from the console.** A data node does not register with the console and does not appear in its node list.
- [L-274] **Graph processor and Cassandra faults.** When Cassandra answers the graph processor's health probe but a single artifact write times out, the artifact is logged and acknowledged, and may not be stored. A Cassandra fault that keeps failing the health probe holds ingest until the probe passes or the graph processor stops; a warning is logged at most once a minute while it holds.
- [L-275] **Supported topology.** One Analytics Processing node per organization and Data cluster is supported; support for more than one is planned for a later release.
- [L-276] **A contested relay address shows as "Status unavailable".** If another party presented this appliance's relay credential while its tunnel was up (in the last 15 minutes), the AI Setup card shows "Status unavailable" and `wfa mcp-relay status` shows "contested". Revoke the address (`wfa mcp-relay off`), enable the relay again (`wfa mcp-relay enable`), run `wfa restart`, give your MCP clients the new address and rotate the personal keys they held.
- [L-277] **A relay address that cannot be revoked from the appliance.** The relay address cannot be revoked from the appliance if node.json holds only one of the relay's handle and credential, for example after a re-run of `wfa configure` or `wfa fetch` could not read the other. In that state `wfa mcp-relay off` stops the relay, says the address is not revoked and exits non-zero, and `enable` refuses. To fix it, copy the missing value back from the node.json.unreadable-<time>.bak copy and run `off` again, or ask WitFoo support (support@witfoo.com) to revoke the address. Once support confirms, remove the remaining relay fields from node.json by hand before you enable again: `mcp_relay_handle` or `mcp_relay_credential`, `mcp_relay_enabled`, `mcp_relay_ack` and `mcp_relay_revoke_pending`, plus `mcp_public_url` if it holds the old relay address.
- [L-278] **Plain-text refusals through the relay.** Through the relay, a refusal the MCP server writes as plain text (an unsupported content type, a malformed request, or a method it does not serve) reaches the client as a status code without its explanatory text. Clients should read the status.
- [L-279] **Vrax import context is as current as the last successful check.** An appliance that cannot reach `app.vrax.io` keeps what it stored and shows the status; nothing is fetched until the next check. Allow outbound HTTPS to `app.vrax.io` for the appliance if you use the Vrax import (its login connection or its feed connection).
- [L-280] **The Vrax import's two connections are kept separately.** The login connection and the feed connection store their data separately, each organization has one login connection and one feed connection, and a refusal on one does not stop the other.
- [L-281] The Vrax import does not use an environment proxy, so an appliance that reaches the internet only through a proxy cannot use it.

- [L-282a] **OCI flow logs: long flows.** An OCI flow that lasts longer than the connector's four-minute guard is never read.

- [L-282d] **Resent artifacts whose id was replaced.** An artifact whose id is replaced on receipt (see Receiving artifacts) gets a new id each time it is received, so a resend that arrives after the receiver's one-minute duplicate window is stored twice.
