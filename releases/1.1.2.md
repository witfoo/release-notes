# WitFoo Analytics 1.1.2

## Summary

WitFoo Analytics 1.1.2 is a **maintenance release** focused on search timing correctness and a
major expansion of data-onboarding coverage. Signal Search now places every artifact on the
timeline by the time the event actually **happened** rather than the time the appliance received
it — so telemetry that arrives minutes or hours late (relayed Zeek/Corelight sensors, store-and-
forward syslog, pull connectors) lands in the search window where an analyst will actually look
for it. Alongside that, more than a dozen parser improvements close real gaps observed on
production fleets. It is a recommended, drop-in upgrade for all 1.1.x deployments — no breaking
changes and no manual migration steps.

## What's New

### Search timing is now event-based

- **Artifacts are searched by event time.** When a parser can read the event's own timestamp,
  Signal Search timelines, windows, and drill-downs now use it. Previously everything was timed
  by arrival at the appliance, so a sensor feed running behind (observed live: a relayed
  Corelight sensor ~3.5 hours behind) appeared in the wrong hours — or, in a defect this release
  also fixes, appeared on the timeline but returned **no rows** when filtered. Timestamps are
  sanity-bounded (up to 30 days late, 1 hour of clock skew); anything outside falls back to
  arrival time, and records written by earlier releases behave exactly as before.
- **"Filter for" pivots use exact matching.** Clicking a value in Signal Search results now
  filters for exactly that value instead of a substring match — matching what the facet panel
  already did, returning precisely what was clicked, and running faster server-side.

### Data onboarding

- **Zeek / Corelight sensors fully extract.** Connection records with ISO 8601 timestamps
  (Corelight's default) previously fell through to a generic classification with no client/server
  addresses extracted, corrupting node correlation for the whole feed. All Zeek timestamp formats
  are now handled, log types are routed by the record's own `_path`, and Corelight extensions
  (layer-2 addresses, VLAN, application tags, shunt counters) are captured.
- **Cisco Secure Network Analytics (Stealthwatch) 7.x.** Modern CEF-format alarms — Data
  Exfiltration, Data Hoarding, Anomaly and related detections — are now fully parsed and
  classified as security signal; the legacy Stealthwatch format continues to work unchanged.
- **Palo Alto PAN-OS SYSTEM logs.** System events (device telemetry, URL-database updates and
  other operational subtypes) from current PAN-OS releases are now recognized and classified
  correctly.
- **Microsoft Graph security coverage.** Alerts from *all* Defender workloads (Endpoint,
  Identity, Cloud Apps, Office 365 and others) are now parsed — previously only Office 365
  alerts were — and Microsoft Secure Score posture snapshots are captured as diagnostic
  telemetry.
- **VMware fleet coverage.** New and extended parsing for vCenter SSO authentication failures
  (including expired/locked accounts), NSX-T distributed-firewall packet logs on ESXi 8
  (`FIREWALL-PKTLOG`), the NSX network-operations agent, ESXi 8 system services (vSAN monitors,
  NFC, image management, SSH service toggles and more), VxRail manager services, and the ESXi
  Envoy reverse proxy.
- **New sources.** Lantronix (Uplogix) Local Manager out-of-band console managers (managed-device
  reachability and job reports), Cisco access-point watchdog telemetry, and HPE ProLiant
  Management Agent storage events.

### Appliance & pipeline reliability

- The automated parser-coverage pipeline now correctly recognizes formats an existing parser
  already handles, eliminating duplicate work and noisy tracking issues, and internal appliance
  service chatter is classified as diagnostics so it can never surface as false security signal.
- Build/publish infrastructure hardening around advisory security scans and release image tags
  (no customer-visible behavior change; removes spurious pipeline failures).

## Upgrade Notes

- Drop-in upgrade for 1.1.0 / 1.1.1 deployments; no configuration or schema changes required.
- Search windows spanning the upgrade moment may show late-arriving records under both their
  arrival hour (records written before the upgrade) and their event hour (records written after);
  this resolves itself as pre-upgrade data ages out of retention.

## Verification

After upgrading, filter Signal Search on a stream delivered by a relayed or lagging source
(e.g. `stream_name = bro` for a Corelight feed): the timeline bars and the result rows should
agree, and record timestamps should match the event times in the raw messages.
