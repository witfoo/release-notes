# WitFoo Analytics 1.1.5

**Released:** 2026-09-19 · **Previous:** 1.1.4 · **Type:** patch

A maintenance release for the 1.1.x line. Most of it closes defects where the product was
**reporting something other than what it was doing** — an assistant that answered from a canned
string, a search that returned fewer rows than it found, a form that stored a value nothing read.

> **Release notes for 1.1.x are hand-authored.** The automated generator computes its commit range
> against the `testing` branch, which belongs to the 1.2.0 line and is 3,501 commits divergent from
> this one. Against 1.1.4 this release is 16 commits; the generator would have reported 27 and
> described the wrong work.

---

## Read this first if you use the AI assistant

### OpenAI and Google Gemini did not work, and nothing said so

If your organization was configured for **OpenAI** or **Google Gemini**, the assistant was not
talking to those providers at all. Their implementations were unfinished placeholders that returned
the fixed text `"Stub response"` to every question, along with invented token counts.

Nothing surfaced this. The provider list offered them as first-class choices, the model dropdown
filled in normally, and saving the configuration succeeded — because the model list was fetched for
real while the *conversation* was not. **Your API key was never actually validated at any point.**
The only symptom was the answer itself.

Both providers are now fully implemented, including tool use, so the assistant queries your real
security data. **If you have been running on OpenAI or Gemini, please see "Action required" below.**

### The assistant could not use its tools on a local model

With **Ollama** — the local, on-appliance provider — the assistant held a conversation but could
reach **none** of its data tools, even though its instructions tell it to always consult real data
before answering. It answered from the model's own knowledge instead.

That is fixed. On a local model the assistant now runs the full loop — question, data lookup,
answer — entirely on the appliance. **For disconnected and air-gapped deployments this is the
difference between an assistant that sounds informed and one that is.**

Summaries and report narratives were never affected; they do not use tools.

### Security work units could auto-resolve on an analysis nothing had checked

When the AI agent is a work unit's primary investigator and finishes every task, the work unit
auto-resolves. That decision looked only at whether the analysis call returned *without an error* —
never at what it returned.

On OpenAI or Gemini, that meant real security work units were being closed on the string
`"Stub response"`.

Auto-resolve now requires each AI analysis to be verifiably complete. Anything partial, empty, or
unverifiable leaves the work unit open for a person. **This fails closed:** work units in flight
across the upgrade carry no quality record, so they will wait for a human rather than auto-resolve.
That is deliberate.

## Action required

**If your organization used OpenAI or Google Gemini for AI analysis, before 1.1.5:**

1. **Re-review any work unit that was auto-resolved by the AI agent.** Those closures were made on
   placeholder text. This release prevents new ones; it cannot reopen old ones.
2. **Expect real provider charges.** These providers now make genuine, billed API calls. Previously
   they cost nothing because they never contacted anyone. If cost matters, review
   **Admin → AI → Configuration** before upgrading.
3. **AI notes recorded on tasks may contain `"Stub response"`.** They are historical records of what
   the AI produced at the time and are left untouched.

**If you configured a Base URL for OpenAI or IBM watsonx.ai:** that field was never read by either
provider and is no longer offered for them. Any stored value is cleared the next time you save that
configuration. Ollama still uses it, as it always did.

**If a non-administrator managed your AI provider settings:** those endpoints now require the
**Manage AI** permission. Viewing settings and using the chat assistant are unchanged.

## Connect Claude Desktop, Cursor or Claude Code to your appliance

WitFoo's 51 MCP tools can now be used from external AI clients over the **Streamable HTTP**
transport those clients speak natively. No bridge or helper process to install.

It is **off by default and requires two separate deliberate steps** — the appliance operator enables
the transport, and an organization administrator enables key authentication and issues a key.
Neither implies the other, so no existing deployment gains a new network endpoint by upgrading.

An API key grants access to **all 51 tools, including write tools.** Treat it as an operator
credential. Setup instructions, client configuration and the full security discussion are in
[`docs/MCP_AUTH.md`](../MCP_AUTH.md).

## Also fixed

**Search returned fewer results than it found.** A search whose filter matched sparsely could report
far fewer results than existed — in the worst case none, while a later page of the same search
returned hundreds. The per-partition read budget was being spent on rows that were then discarded,
so the budget ran out before the matches were returned.

**Wi-Fi events from Arista access points were discarded.** Roughly 18,000 events per week per fleet
were dropped because two parts of the parser recognised different sets of device identifiers. Both
now read one list.

**A LimaCharlie connector failed silently.** Authentication failures produced no error and no data —
the integration simply appeared to have nothing to report.

**A Zscaler connector queried an endpoint that no longer exists**, so firewall logs never arrived.

**Deduplication never released memory, and summary alerts were rate-limited to one per window.** The
cache cleanup examined a single entry per pass and stopped. On long-running appliances the cache grew
without bound.

**Smaller fixes:** five CyberGrid subscriber management endpoints returned 404 · a CyberGrid edit tab
could not be opened · the work-unit "All Statuses" filter excluded some statuses · the Feed Type
filter offered a fixed list instead of what the data contains · three parser catalog entries pointed
at no backend.

## Security

Two issues are fixed in this release. Both required an authenticated account on your appliance.

**A provider configuration field was used to build an outbound address without validation** (CWE-918).
A crafted value could redirect a provider request — and the credential sent with it — to a host of
the submitter's choosing. The field is now restricted to the format it was always meant to hold, and
re-checked at the point of use.

**AI provider configuration endpoints did not check permissions.** Any authenticated user could
change the provider, API key, endpoint and automation settings. These now require **Manage AI**.
Read-only views and the chat assistant are deliberately unchanged, so no one loses access they
already had.

## Upgrade

Standard upgrade path. No schema migration, no configuration change required.

Behaviour that changes on upgrade **without any action on your part**:

| Change | Who is affected |
|---|---|
| OpenAI/Gemini make real, billed API calls | organizations configured for those providers |
| AI auto-resolve withheld for in-flight work units | anyone using AI response automation |
| Base URL no longer collected for OpenAI/watsonx | anyone who had set one |
| AI configuration writes require Manage AI | non-administrators who managed AI settings |

Everything else is additive or a straightforward defect fix.

## Known limitations

- **Streaming responses** are implemented for IBM watsonx.ai only. The capability table previously
  claimed four providers; it now reflects what ships. No product surface uses streaming today.
- **Two of the 51 MCP tools are placeholders.** `search_incidents` and `get_incident_details` are
  registered and documented but not yet backed. They are excluded from the built-in assistant.
- **MCP OAuth authentication remains reserved.** Key-based authentication is the supported method.
